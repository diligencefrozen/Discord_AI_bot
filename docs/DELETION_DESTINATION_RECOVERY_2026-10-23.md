# 도리봇 기존 공용 삭제 기록 채널 전송 복구 — 2026-10-23

이전 복구 기록입니다. 현재 기준은 [V7 공용 상세 삭제 기록 복구](PUBLIC_DELETE_HOTFIX_V7_2026-10-23.md)이며
**네 목적지 모두** 실전 확인이 필요합니다. 아래 이전 로컬 의존성/전송 검증 한계와 혼동하지 마세요.

## 목적지 ID와 실제 의미

**아래 세 ID는 삭제가 발생한 채널의 ID가 아니라, 삭제 기록을 받는 기존 `#record-channel` 목적지 ID입니다.** `main.py`의 `LOG_ROUTES` 최상위 키에서 직접 확인했습니다.

| 기존 삭제 기록 수신 채널 ID | 용도 |
| --- | --- |
| `1064823080100306995` | PUBG M : 배사모 |
| `1383468537229738156` | 아사모 서버 |
| `1065283543640576103` | 삼사모 서버 |

기존 네 번째 수신 채널 `1383987919454343269`도 유지했습니다. **채널을 새로 만들거나 이름/ID를 변경하지 않았습니다.** 공용 기록 채널은 서버마다 기존 한 곳뿐입니다.

## 이번에 손본 전송 경로

1. 이전에는 `bot.get_channel(channel_id)`에 수신 채널이나 원본 채널이 존재하지 않으면 기록을 포기할 수 있었습니다. 이제 `bot.fetch_channel(channel_id)`로 기존 ID를 추가 조회합니다. 성공과 실패 모두 30초 이내 캐시해 반복 REST 요청 폭주를 막습니다. 가져온 채널의 ID와 서버 ID가 일치하지 않으면 전송하지 않습니다.
2. 미리 지정된 `LOG_ROUTES` 원본 채널에서 발생한 삭제는 **목적지가 Discord 캐시에 없어도** 전송을 시도합니다. 자동 감시하는 새 채널도 단일 목적지 확인 후 전송합니다.
3. 공용 목적지에서 읽을 수 있는 모든 회원이 원본 채널을 볼 수 있을 때만 **원문과 이모지/첨부파일/검열 사유가 들어 있는 상세 카드**를 보냅니다. 원본이 비공개이거나 열람 범위를 증명할 수 없으면, 공개 채널에 작성자·채널·원문·파일·ID를 알리지 않는 **익명 제한 기록**만 전송합니다. 서버 내 비공개 채널 정보를 일반 사용자에게 노출하지 않기 위한 안전 조건입니다.
4. 기존 수신 채널에 봇의 `View Channel`, `Send Messages`, `Embed Links`가 없거나 수신 채널 자체에 접근할 수 없으면 계속 전송할 수 없습니다. 이런 경우는 전송이 성공했다고 표시하지 않으며 실패 원인을 남깁니다.
5. 봇 기동 시 기존 네 목적지 모두에 대해 `deletion_audit_destination_probe` 로그를 남깁니다. 읽을 수 없는 채널은 `channel_missing_or_forbidden`, 임베드 전송 권한이 없으면 `destination_bot_embed_links`, 정상이면 `ready` 등으로 나타납니다. 이것은 메시지를 보내지 않는 가벼운 사전 확인입니다.
6. `/관리 → 삭제 로그 전송 테스트`도 목적지를 캐시에서 못 찾으면 REST로 조회한 후 기존 수신 채널에 실제 테스트 카드를 보냅니다. 별도의 관리자 로그 채널은 만들지 않습니다.

## Northflank 환경변수

```dotenv
DELETION_PUBLIC_LOG_ENABLED=1
DELETION_PUBLIC_LOG_INCLUDE_CONTENT=1
DELETION_LOG_ALL_GUILD_CHANNELS=1
```

기존 `LOG_ROUTES` 수신지에는 새로운 환경변수가 필요하지 않습니다. `DELETION_LOG_EXTRA_SOURCE_CHANNEL_IDS`는 **원본 채널을 추가**할 때만 사용하며 삭제 로그의 수신 채널을 변경하는 값이 아닙니다.

## 배포 직후 3서버 검증 절차

1. 각 서버에서 도리봇이 기록 수신 채널을 볼 수 있고 `메시지 보내기`, `링크 첨부(Embed Links)` 권한을 갖는지 확인합니다. 원본 채널에도 도리봇의 `채널 보기` 권한이 필요합니다. **파딱(특별 관리자) 개인에게 관리자 역할을 주지는 않습니다.**
2. Northflank 시작 로그에서 `event=deletion_audit_destination_probe destination_id=<ID> result=ready`를 세 ID 각각 확인합니다. `channel_missing_or_forbidden`이라면 봇 초대 서버/ID/채널 권한부터 확인합니다.
3. 각 서버 파딱 계정으로 `/관리 → 삭제 로그 전송 테스트`를 누릅니다. **세 기록 채널에 각각 테스트 카드가 실제 도착하는지** 확인합니다. 검사 화면만 `ready`인 것으로는 충분하지 않습니다.
4. 원본이 일반 공개 채널일 때 `테스트123`을 보내고 직접 삭제합니다. `작성자/채널/원문/시각`이 나오는지 확인합니다.
5. 다른 새 공개 채널에서 동일 검사를 반복합니다. 비공개 채널 테스트에서는 **원문이 절대 공용 채널로 전송되지 않는지** 확인합니다.
6. `시321133발` 등 기존 금칙어 자동 검열도 시험합니다. 공개 원본에서 봇이 삭제한 메시지는 단일 공용 로그에 `자동 검열`과 원문, 탐지 정보가 표시돼야 합니다.
7. 실패 시 Northflank 로그의 `event=deletion_audit result=skipped/failed reason=...`, `/관리 → 운영 상태`의 최근 실패 사유를 확인합니다. 전송 `403`은 도리봇 자신의 권한/채널 오버라이트 문제입니다.

## 제한 및 검증 범위

- 캐시에 없던 과거 삭제 메시지의 **본문 자체는 Discord에서 복구할 수 없습니다**. 삭제 이벤트가 수신되더라도 원문을 모르면 카드에 확보 불가로 기재합니다.
- Discord Developer Portal에서 **Message Content Intent**가 활성화돼 있어야 정상적인 본문 접근이 가능합니다.
- 기록 채널의 봇 기록 메시지를 다시 삭제해 무한 재귀되는 현상을 피하려고, **공용 기록 목적지 채널 안에서 발생한 삭제는 감시하지 않습니다.**
- 정확한 실제 전송 여부는 **Discord에 배포해 검증해야 합니다**. 로컬에서는 Python 구문 검사 및 Discord 전송 동작을 모사한 격리 테스트만 수행했습니다(실제 `discord.py` 다운로드가 불가한 환경).
